# Technical and on-page SEO audit of www.rexity.ai (Rexity Labs UG)

Audit date: 2026-09-28. **Method caveat (read first):** the sandbox's egress proxy denied every direct request to `www.rexity.ai` and `rexity.ai` (curl: `CONNECT tunnel failed, response 403`; WebFetch: `EGRESS_BLOCKED`), and also to web.archive.org, r.jina.ai, vercel.com, Bing and DuckDuckGo. So the live HTML could **not** be fetched. What was possible: (a) Google's index via WebSearch, and (b) the GitHub repository `sunnyth7/Rexity.ai-website`, whose `main` branch is described in every recent commit as "Mirror of the built site … Preview only; merge to main = deploy" ([commit d825e5c, 2026-09-28 15:33 UTC](https://github.com/sunnyth7/Rexity.ai-website/commit/d825e5cdcc2f10b989e62acba57ec48c0ebec9ec)). Two snapshots were analysed and are labelled throughout:

- **"main@d825e5c" = presumed live** — remote `origin/main` fetched 2026-09-28 (4 release-candidate commits newer than the local clone: fb10148 09:27, 881bda3 13:20, e9796be 15:20, d825e5c 17:33 CEST).
- **"local@15ec2b7"** — the local clone's `main`/HEAD as of 2026-09-27 23:01 CEST (the state the task called "the repo"). Where the two differ, both are reported.
- **"Google index"** — what WebSearch `site:` queries returned on 2026-09-28.

Nothing that requires an HTTP response (redirect chains, status codes, response headers, actual rendered page weight, Core Web Vitals field data) could be observed; those are listed under Gaps with what the config *should* produce.

## Key Question 1 — Crawlability: robots.txt, sitemap.xml, canonicals, redirects, trailing slashes, 404, vercel.json

### Takeaway
robots.txt allows everything and points to the sitemap; the sitemap in main@d825e5c lists 30 URLs (29 in local@15ec2b7), all with `lastmod` mass-set to the build date; canonicals are self-referencing on every indexable marketing page but absent on /impressum and /datenschutz (which are in the sitemap); Vercel is configured for clean URLs, no trailing slash, `fra1` region and four 308 redirects, but the www/non-www and http→https behaviour is domain-level Vercel configuration that is not in the repo and could not be observed.

### Inferences
- With `cleanUrls: true` and `trailingSlash: false`, Vercel will serve `/web` from `web/index.html`, redirect `/web/` → `/web` and `/impressum.html` → `/impressum` (308). That matches the canonical form used, so duplicate-URL risk from slashes/extensions is low — but this is inferred from the config, not observed.
- Mass-resetting every `lastmod` to the deploy date (main@d825e5c) removes the signal's value; Google documents that it ignores lastmod when it is consistently inaccurate. The previous snapshot was better here.
- The `/rexity-omi → /` redirect and `/web/web-development → /web/web-design` redirect suggest earlier URL structures (an "omi" product page and a "web-development" slug) that may still be in Google's index; whether they are is a gap.
- 12 indexable-but-unlisted pages (app privacy/deletion pages, four English `/systems/*` stubs) are discoverable by crawlers through the `/privacy` hub or by direct links from app stores and will be treated as part of the site.

### Gaps
- Actual HTTP behaviour (http→https, non-www→www, 301 vs 308, trailing-slash redirects, HSTS header presence, 404 status code for unknown paths) could not be observed because the proxy blocked all requests to the host.
- Whether Vercel Analytics, the domain redirect and the production alias are configured in the Vercel dashboard cannot be verified from the repo.
- Whether Google Search Console is actually verified/used (the file exists; usage is unknown).
